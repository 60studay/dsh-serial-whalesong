# AI 双机协作工作流（实战总结）

> **这不是理论，是一场真实项目踩出来的。**
> 两个 AI 协作开发同一个项目，跑了 200+ 轮，上下文被压缩十几次，仍然没丢活。
>
> **核心问题**：上下文一压缩，AI 就失忆，然后开始重复劳动 / 反复问同一件事 / 忘记分工。

## 零、先破除一个错误想象

**很多人第一反应是"按能力分工"**：一个 AI 有硬件、另一个没有，所以一个测、一个写。

**这个想象是错的**（我一开始就是这么想错的）。

真实的约束通常是这两条：

| 约束 | 表现 |
|---|---|
| **成本** | 一个模型便宜、上下文小；另一个贵、上下文大、能力强 |
| **上下文预算** | 谁在什么时候被压缩，谁就失忆 |

**两个 AI 跑在同一台机器上、共用同一套工具、都能操作真实硬件。**

所以真正的分工不是"谁能做"，而是：

> **便宜的那个负责把人的话精炼成需求、做验证、守纪律；
> 贵的那个负责在有限上下文里做高价值的实现。**

这个分法比"能不能"稳得多——因为能力是随时可变的（换模型就变），
而"谁的上下文更值钱"是稳定可算的。

## 一、四条核心机制

### 机制 1：分工写死，而且要写在文档里

**血的教训**：测试方（有硬件那个）在实测时顺手把 bug 修了，越界改了 6 处代码。
用户的原话是"这活儿不是交给你干的"。

**为什么这会出事**：
- 测试方的判断建立在"我看到的这一台设备"上，容易过度拟合
- 改动没有经过写代码那个 AI 的架构视角
- 两个人同时改同一个文件 → 冲突、互相覆盖

**做法**：

| 角色 | 只做这些 | 绝不做这些 |
|---|---|---|
| **实现方**（贵、上下文大） | 写代码、设计架构、自查 | 声称"完成"而不自测 |
| **协调方**（便宜、上下文小） | **把人话精炼成需求**、实测、给证据、写自检、守文档 | **改业务代码** |

**注意**：两个 AI **都能**操作硬件、**都能**跑测试。
分工的边界是**上下文预算和成本**，不是能力。

**关键**：分工要写进**进度文档**，不能只靠口头约定。
因为上下文一压缩，口头约定就没了，AI 会"顺手"越界。

> 唯一例外：**一行就能确定的、阻塞测试的 bug**（比如函数少传一个参数）。
> 这种可以临时补，但必须在通讯板标注"测试方为了让测试跑起来打的补丁，请覆盖"。

---

### 机制 2：通讯板（Append-only，新的在最上面）

**作用**：两个 AI 直接对话，人只负责说"去看通讯板"。

**格式**：

```markdown
# 【测试方 → 开发方】

## 2026-11-06 23:28 · 🔴 你把 4.8 标成"完成"了，但那个 bug 还在

### 事实
（贴命令 + 真实输出，不要描述）

### 根因
（指到文件和行号）

### 修法
（给代码，1 行也要给）

### 其余部分我全测了，都过
（先说好的，避免对方以为全盘否定）
```

**四条铁规**：

1. **新的写最上面**（倒序），双方都只看最新
2. **带时间戳和编号**，能和 bug 清单对上
3. **贴真实输出**，不写"有问题请修"这种空话
4. **只追加不删**，历史是证据

**为什么有效**：人和 AI 都只需要说"看通讯板"，不用来回转述。
转述 3 次必然失真。

---

### 机制 3：进度总账（唯一权威，而且要短）

**这是防上下文压缩的核心。**

**问题**：文档越攒越多。这个项目最后有 11 个文档、9000+ 行。
上下文一压缩，AI 不可能读完，于是开始瞎猜。

**做法**：一份**不超过 200 行**的总账，回答一个问题：**现在到底做到哪儿了。**

必须包含的 8 块：

| 块 | 内容 | 为什么必须有 |
|---|---|---|
| 1 | **当前状态一句话** | 压缩后第一眼就要知道 |
| 2 | **硬事实** | 版本/提交/工具数/自检数，不用去查 |
| 3 | **已完成** | 防止重复劳动 |
| 4 | **下一步（带顺序和负责方）** | 防止站错位置 |
| 5 | **卡在哪** | 待对方回复的事项 |
| 6 | **测试环境** | 端口、场景、模式、硬件 |
| 7 | **铁律** | 每次改动都要过一遍 |
| 8 | **已知坑** | 踩过的别再踩 |

**写作纪律**：
- 上面写"现在是 v2.1.0，下一步是做 X"，不要写"我们讨论过 X 的三种方案"
- **细节去别的文档**，总账只记状态
- 每完成一件事 → **立刻**更新，不等攒

> **一句话**：总账不是日记，是仪表盘。

---

### 机制 4：自检检查自检（防止文档自己过期）

**这是最容易被忽略、但最关键的一环。**

总账是手写的，代码是自动变的。**一份会骗人的总账，比没有总账更糟**——
因为它是上下文压缩后第一份被读的文件。

**做法**：写一个脚本，机械核对总账里能验证的数字。

```python
# 核对项（都可机械验证）
1. 总账写"8 个工具"  == 代码里实际注册几个
2. 总账列的工具名    == 实际工具名
3. 总账写"N 个自检"  == 磁盘上实际 selfcheck_*.py 个数
4. 总账写"M 项全绿"  == 各脚本实际报告的数字之和
5. 总账写"X 行"      ≈ 关键文件实际行数   （用容差，别要求精确）
6. 总账记的提交号    ≈ git HEAD          （用"落后几个提交"判断，别要求相等）
```

**两个必须注意的实现细节**：

- **提交号不能要求相等**：总账里写的是"写总账那一刻"的 HEAD，
  而把总账提交上去这个动作本身就会产生新 HEAD。永远差至少一个。
  → 改成"落后 N 个提交，超过阈值才算过期"。
- **行数用容差**：加两行注释不该报错。
  → 容差 40 行是合理的。

**必做的验证**：**故意把总账改错 3 处，确认脚本能抓到。**
抓不到的检查等于没有。

### ⚠️ 自检的第二条铁律：它必须能扛住它要测的那个故障

这是踩出来的，而且很隐蔽。

有个自检是"测某函数不会崩"，写法是：

```python
try:
    result = the_function()
    check("不该崩", True)
except BridgeError as exc:        # ← 只捕"预期内"的异常
    check("错误类型对", exc.kind == "config")
```

**如果 bug 抛的是 `TypeError`（不在 `BridgeError` 里）会怎样？**

→ 异常漏出去 → **整个自检脚本死在第 1 项** → 后面 7 项根本没跑 →
用户看到的是一屏 traceback，**没有 PASS/FAIL 统计**。

**最需要它报警的时候，它自己先倒了。**

**修法**：加一个兜底的 `except Exception`，转成一条 FAIL，然后照常出统计。

```python
except BridgeError as exc:
    check("错误类型对", exc.kind == "config")
except Exception as exc:                    # ← 必须有
    check("不应抛出非预期异常", False,
          "%s: %s" % (type(exc).__name__, exc))
```

**还要在整个入口包一层**，保证任何意外都能出统计：

```python
if __name__ == "__main__":
    try:
        sys.exit(main())
    except SystemExit:
        raise
    except Exception as exc:
        print("自检没能跑起来：%s: %s" % (type(exc).__name__, exc))
        print("这本身就是失败。")
        sys.exit(1)
```

**自查方法**：搜你所有自检里的 `except`，逐个问：
**"如果 bug 抛的是别的异常类型，这个测试会怎样？"**
答"会崩"就是漏洞。

> **一句话**：一个"测 X 不会崩"的测试，必须自己能扛住 X 崩。
> 否则它只会在风平浪静时显示绿色——那毫无价值。

## 二、踩过的坑（都是真的）

| # | 坑 | 后果 | 规避 |
|---|---|---|---|
| 1 | 测试方顺手改业务代码 | 分工失效、冲突、用户不满 | 分工写进文档，只允许改阻塞测试的一行 bug |
| 2 | 开发方标"完成"但没自测默认路径 | 参数可选的新工具，AI 最自然的用法必崩 | **标完成前先跑一遍"最自然的用法"** |
| 3 | 只测显式传参的路径 | 漏掉"省略参数"这条最常用路径 | 每个可选参数都要测"不传"的情况 |
| 4 | 拆分文件时漏 import | 接口 500，**纯逻辑自检完全测不出** | 加 HTTP 层自检；改完立刻访问接口 |
| 5 | 自检数字漂亮但没覆盖出问题的那层 | "157 项全绿"掩盖了两次 HTTP bug | 自检要按**层**覆盖，不是按数量 |
| 6 | 两份进度文档不同步 | AI 读到过期信息，做错决策 | 指定一份"唯一权威"，其余标注"已过期，信总账" |
| 7 | 后台起服务时加 `\| Select-Object -First N` | 管道读够就关闭上游，**服务被静默杀掉** | 后台任务不要接管道 |
| 8 | 两个 AI 同时改同一目录 | 一方起的服务被另一方关掉，看起来像"灵异事件" | 起步前先 `git status` 看有没有别人未提交的改动 |
| 9 | 自检只 `except` 具体异常类型 | bug 抛别的类型时，**自检自己崩**，报不出 FAIL | 加兜底 `except Exception`，入口再包一层 |
| 10 | 以为分工是"有硬件/无硬件" | 分错边界，越界改代码 | 按**成本和上下文预算**分工，不是按能力 |

## 三、一个反直觉的发现

**"自检全绿"不能作为"改动是对的"的证据。**

这个项目 157 项自检全绿的情况下，连续漏了两个真 bug——都出在 HTTP 层，
而 157 项一个都没测 HTTP。

所以后来补了 `selfcheck_web_api.py`（55 项），并且**实测它能抓到那两个 bug**：
- 把 import 删掉 → 抓到 `status=500`
- 把 bug 改回去 → 抓到 `port_busy`

**结论：自检的价值不在数量，在于"它测的是不是真会坏的那一层"。**

## 四、可复用的骨架

```
项目/
├── _需求文档/
│   ├── 进度总账.md        ← 唯一权威，<200 行，压缩后先读这个
│   ├── 代码地图.md        ← "我想改 X，改哪个文件哪一行"
│   ├── AI协作通讯板.md    ← append-only，新的在最上面
│   ├── 功能规划清单.md    ← 后续要做什么（带顺序和依赖）
│   └── 已知坑.md          ← 踩过的别再踩
├── selfcheck_*.py         ← 按"层"覆盖，不是按数量
└── README.md              ← 顶部指向进度总账
```

**三处入口都要指向总账**（否则压缩后不会去看）：
1. `_需求文档/README.md` 顶部
2. `代码地图.md` 开头
3. 项目根 `README.md`

## 四点五、这套工作流叫什么，以及为什么**不能信任对面**

### 名字：规格 → 实现 → 独立复验（SBI）

**不是 plan-and-execute。** 那个模型是单向的：一方出计划，另一方照做，
执行方没有质疑权。我们不是。

| 环节 | 谁做 | 产出 |
|---|---|---|
| 规格 | 便宜方（上下文小） | 需求 + **验收标准**（可机械检查） |
| 实现 | 强模型方 | 代码 + **自测证据** |
| 独立复验 | 便宜方 | **重新跑一遍**，不看对方结论 |

三个特征：
1. **双方都能驳回对方** —— 不是上下级
2. **验收标准在实现之前定** —— 否则会被实现带着跑
3. **复验是独立重跑，不是审阅文字** —— 这是和 code review 最大的区别

### 为什么不能把对面的话当真理

**因为真的会错，而且双向都会错。**

同一个项目里：

| 谁错 | 事实 |
|---|---|
| 实现方 | 把功能标"完成"并提交，但参数可选的那条路径必崩。重跑才抓到 |
| 协调方（我） | 断言某函数"零调用方"，其实只 grep 了一个文件 |
| 协调方（我） | 断言"工具表在会话开始固定" —— **纯属猜测**，被用户当场纠正 |

**两方都会错，而且说"零调用方"的那个错的次数还多一些。**

### 核心原则：权威不在任何一方 AI 手里

> **权威在机械可验证的东西里：自检脚本、真机实测、编译器、git。**

落到五条要求：

**1. 消息必须分「声明」和「证据」**
```json
{"claim": "X 已完成",
 "evidence": {"cmd": "...", "stdout": "...", "exit": 0},
 "not_verified": ["我还没测的路径"]}
```
**`not_verified` 字段最重要** —— 大部分事故都发生在"没说没验什么"。

**2. 默认不采信**。通道只传，不背书。看到证据的第一反应是"我能不能重跑"。

**3. "复验"是一等消息类型**。`verify_req` / `verify_res`，
且 `verify_res` 必须附自己跑出来的输出，不能只写"同意"。

**4. 禁止"共识即真理"**。两个 AI 都同意也可能都错。
唯一锚点是外部世界：自检过没过、硬件回没回包、编译器报没报错。

**5. 什么算证据，写死清单**

| 算 | 不算 |
|---|---|
| 命令 + 完整 stdout + 退出码 | "我测过了" |
| 自检的 PASS/FAIL 数字 | "自检全绿" |
| 真机回包原始 hex | "回包正常" |
| 编译器输出（含 warning） | "编译通过" |
| git 提交号 | "改好了" |

**判断标准：别人能不能照着复现。**

### 一条最实用的话

> **没验就说没验，不丢人；说验了其实没验，才是事故。**

### 还有一条：让复验比信任更便宜

如果复验花的力气比直接信任还大，人（和 AI）就会选择信任。

所以通道/工具要支持**一键复验** —— 在网页上点一下就把 `evidence.cmd` 重跑一遍。
**降低复验成本，否则上面所有原则都会沦为空谈。**

## 五、给 AI 的提示词（可直接抄）

放在总账开头：

```markdown
> **给 AI 的提示**：上下文被压缩后，**先读这一份**（不到 200 行）。
> 不要一上来读通讯板（可能几千行）。
>
> 每次状态变化立刻更新本文件。本文件过期 = 事故。
```

## 六、什么时候不适用

- **单人、单次任务**：不需要，直接做
- **纯软件、无环境差异**：写代码的 AI 自己能跑，不需要双机
- **不要求可追溯**：如果只是聊聊天，别搞这些仪式

**这套东西的成本**：每次做完一件事多花 1 分钟更新文档。
**收益**：上下文压缩 10 次以上仍然能接着干，不重复劳动、不站错位置、不失忆。

## 七、一句话总结

> **AI 会失忆，但文件不会。**
> 把"现在什么状态"从 AI 的脑子里搬到磁盘上，
> 再写一个脚本保证这份记录不会自己过期 —— 这就是全部。

## 八、2026-11-09 ~ 11-11 新增的教训（这三天补的，前七节没写）

> 每条都对应一次真实事故。**新会话先读这一节。**

### 8.1 自检全绿 ≠ 装得上（最贵的一条）

v2.2.5 发布时：**453 项自检全绿**，但插件**一步都加载不了** —— 新工具 `serial_loopback` 的 `render` 写在了 `output` **外面**，DSH 加载校验拒绝，**整个插件被废**：11 个工具全消失、侧边栏报红。

**判据改成"真装一遍"**：

```
□ 全量自检绿
□ 从 tag 真装一遍 → 工具数对不对、每个工具 output 里有 schema + render
□ 打开页面 → 能发一条命令
```

**教训**：能被"加载器拒绝"的东西，只有让加载器真跑一遍才能证明它不坏。推断、看代码、自检断言都替代不了。

### 8.2 "改 JS 必须重启" 踩了三次

`tools/*.js`、`helpers/*.js`、`index.js`、`client.js` 都是进程启动时的快照：

```
① 黑窗修复（helpers/autoopen.js）—— 以为没修好
② python 探测路径（index.js）—— 以为没修好
③ autoBaud 输出 schema（tools/serial.js）—— 以为没修好
```

**规矩**：改完 JS，提交说明必须写"需重启 DSH 才生效"；验收前先重启。

### 8.3 显示类 = 功能级（用户 11-11 改的口径）

我原来把"文案/条数/标签"归为 cosmetic、允许攒批。用户否了："问题不大，也不难，但很影响体验，而且还很多漏过去了。"

**新口径**：界面上"看得不对"和"发不出命令"同档，**当版必修，不许攒批**。理由：用户靠界面判断真假，界面不精确 = 不可信 = 不能用。

### 8.4 新加的路径，要过一遍"旁路清单"

同一类 bug 反复出现：新加一条路径，总会漏掉某个已有环节。

| 新东西 | 漏掉的旁路 |
|---|---|
| push_frame 广播 | 只投"最近活跃"一个实例（1.57） |
| 帧带 port | 日志行没记 port（1.82）、页面自发帧没 port（1.88） |
| 危险命令 | 前缀匹配把查询命令也拦了（1.76） |
| 新工具 loopback | 没进"自动开网页"白名单（1.87） |

**通用问法**："这条新路径要经过哪几个已有环节？每个环节都补了吗？"
清单：**解析 → 发送 → 帧 → 日志 → 页面 → 自检 → 文档**，逐项打勾。

### 8.5 环境专属的坑写进"设备知识"，不要埋进代码注释

```
Windows 起网页实例弹黑 CMD 窗口 → CREATE_NO_WINDOW
Store 空壳 python.exe（WindowsApps 别名）→ 探测要跳过
打开串口默认拉 DTR → 某些模块复位（HC-05）
AT 波特率跟随 AT+UART 设置
克隆固件 hc05V2.3_le 的配对码是 6 位
```

这些不是代码逻辑，是环境事实。写进 `protocols/*/protocol.md` 或 `packs/*`。

### 8.6 串口独占 —— "谁都看得见"要装驱动

别的程序占着口，我们连句柄都拿不到。只有三档：①全走我们（现状）②虚拟串口对（com0com，可选）③USB 层嗅探（重武器）。规划记为 **E10**；铁律：**可选、只抄不拦、装前提示风险**。

### 8.7 交接靠文件，不靠"记得说"

上下文压缩不可预测（轮数取决于 token）。所以：**每次发版 / 派工 / 验收完，立刻更新《交接快照》顶部**。

固定三个地方：**交接快照**（一页）、**待办清单**（要什么 + 判据）、**通讯板**（对话）。压缩后先读快照，再读待办，最后才翻板子。

### 8.8 竞品对照是方法，不是需求

装 `dsh-serial-sifarcrt` / `dsh-elab-cockpit` 只为一件事：**同一任务两边各跑一遍**，看它好在哪 / 能不能学 / 值不值得学。

**纪律**：不因别人有就做，也不因别人有就停自己的；学来的实现必须比原实现简单。（实证：它报 `.NET 信号灯超时`，我们报"被占用 + 3 条原因 + 下一步"——这条我们赢。）

### 8.9 我犯过的一个操作错误：覆盖文件没先读

搬内务时直接 `write` 覆盖了通讯板，3963 行历史没了；今天又差点覆盖这份工作流文档（用 `git checkout --` 恢复才救回来）。

**规矩**：**覆盖前必须先读**；能 `append`/`edit` 就不用 `write`；被 git 跟踪的文件改坏了，先 `git checkout --` 恢复再说。
