## 一、跨口环回：为什么它是"能力"而不是"便利"

### 现场

那位 AI 要验证两个 HC-05 是否真的配上了。唯一可靠的判据是：

```
从主机口写  →  数据走无线  →  从从机口读出来
```

插件当时只能 `serial_send`（同一个口发、同一个口收）。于是它开了两个 .NET 句柄自己干，
结果：**网页和日志里一个字都没有**，用户的第一反应是"插件没工作"。

它自己给这件事定了性（原话）：

> 上一次我绕过场景匹配是**思维惯性**（插件已修好，我还在用老办法）；
> 这一次绕过插件是**能力缺失**（插件根本不支持"写 A 读 B"）。

### 设计

```
serial_loopback
  from     写入的口（如 COM10）
  to       读取的口（如 COM7）
  data     写出去的文本
  expect   可选：读侧出现它才算 matched=true
  baud     两个口共用（默认 115200）
  timeoutMs 读侧最长等多久（默认 1500）
```

实现要点（都在 `serial_bridge/loopback.py`）：

| 点 | 为什么 |
|---|---|
| 两个口都 `port_lock` | 防止和定时发送 / 网页 / 另一个 AI 抢口；跨进程互斥 |
| 先写后读，读侧**持续读到 expect 或超时** | 无线链路的时延不确定，不能假设"一问一答立刻回" |
| `expect` 用**字节子串**匹配，不是"完全相等" | 设备常带 `\r\n`、提示符、前缀 |
| 任何一侧打不开 → 结构化错误（`port_busy` / `no_device`） | 别让调用方猜"是我写错了还是口被占了" |
| 收发都进日志，并**推一帧上页面** | 这是"绕过插件就看不见"的反面：用了工具，就一定看得见 |
| 不猜协议、不改编码 | 它就是个搬运工；协议知识属于 `protocol.md` |

### 边界（明确不做）

- **不做**多口并发收发（一次只一写一读）。多设备身份见待办 1.75。
- **不做**自动重试。链路不通就是不通，重试会把"配对没成功"掩盖成"偶发丢包"。

## 二、危险命令：为什么"文档说别发"不够

### 现场

HC-05 兼容固件的 `AT+BIND?` **不是查询**：它把 `+BIND=` 字面量写进绑定地址，
查一次坏一次，主机从此永远 `CONNECTING`。而且 `AT+RESET` 救不回来，只能断电。

只写在 `protocol.md` 里够不够？**不够**。AI 不读文档，或者读了也照发 ——
文档是"告知"，不是"阻止"。

### 设计：两处并存，强度不同

| 位置 | 性质 | 谁消费 | 内容 |
|---|---|---|---|
| `protocols/<场景>/protocol.md` | **硬性要求**（人看的设备事实） | 人、AI 读文档 | 为什么危险、现场长什么样、正确做法、上电顺序 |
| `protocols/<场景>/config.json` → `dangerous_commands` | **运行时闸门**（机器执行） | `serial_bridge/dangers.py` | `{command, why, safer}` |

匹配规则：`command` **前缀匹配**（`AT+BIND` 同时盖住 `AT+BIND?` 与 `AT+BIND=xxx`），
大小写不敏感。

拦截行为：

```json
{"ok": false, "error": {
  "kind": "dangerous_command",
  "message": "这条命令在这个设备上是危险的：…（why）…。替代做法：…（safer）…",
  "hint": ["确认要发就加 --yes（工具里是 confirm: true）", "这类命令通常有替代做法…"]
}}
```

**为什么是"确认"而不是"禁止"**：有些场合确实必须发（恢复出厂、救砖）。
护栏的目标是"别让它悄悄发生"，不是"永远不允许"。

### 设备知识 vs 通用规则

`dangerous_commands` 是**场景级**配置，不是代码常量。理由：

- 哪些命令危险**取决于固件**，同一个 `AT+BIND?` 在正版 HC-05 上可能只是查询；
- 新设备接入时**不该改代码**就能加护栏。

## 三、顺带确定的一条：场景歧义不该废掉整个场景

两块同型号 CH340 同时插着时，`match: "CH340"` 永远歧义。以前直接抛错 → 场景"整体不可用"
（`serial_info` / `serial_read` / 日志都跟着不好用）。

现在：发送成功会记住 `last_port`（写进场景状态），解析歧义时**优先它**，
`source` 标成 `preferred:last_port`（用户看得到"这是沿用的，不是又猜对了"）。

这对应反馈里的 `prefer` 建议；`exclude` 白名单暂时不做（没有真实需求前不加配置面）。
